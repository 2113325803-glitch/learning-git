## 第 0 章 先给大脑装一个"降维引擎"

### 0.1 你的困境不是"笨"，是缺一层抽象

你说："知道概念但不会手写，无法在脑海中想象运行过程。"

这是一个**极其典型**的现象，原因只有一个：

> **你还没有一个可以把算法"挂"上去的思维模型。**

有的人靠数感（数学好），有的人靠画图，有的人靠抽象。

而你的强项是 **OOP**。那我们就用 OOP 来"降维打击"所有算法。

先回忆 OOP 的本质：

```
OOP 的本质 = 找出"会变的东西"和"不变的东西"
             把会变的东西封装成「属性」，用「方法」作为驱动它的流程。
```

好，现在把所有算法都翻译成 OOP 语言：

| 算法里的东西 | 用 OOP 视角看 | 一句话人话解释 |
| --- | --- | --- |
| 数组 `arr` | 一个**容器对象**（类似 `self.data`） | 它有"长度"属性和"按下标取值"的方法 |
| 指针 `left / right / mid` | **对象的三个状态属性** | 指针移动 = `self.left = ...`，纯粹是改状态 |
| 循环的每一轮 | **一次状态迁移** `state -> new_state` | 和 `while not self.done(): self.step()` 没区别 |
| 递归 | **对象在自己的方法里再创建一个自己** | 完全等价于 `node.left.visit()` |
| 记忆化 / 动态规划 | **一个 `dict` 缓存 + 状态转移** | 就是"对象池 + 缓存命中" |
| 图 | **`Node` 类和 `Edge` 类的集合** | 你在 OOP 里最熟的东西 |

> **把这张表背下来。**
> 以后看到算法不要想"数学"，要想：**这里面有几个对象？谁是它们的属性？每轮循环谁的状态变了？**
> 这一句话，能解决你 80% 的"想不出运行过程"。

### 0.2 四步阅读法（以后每一章都这样读）

碰到任何一个算法，按顺序走，**不要跳步**：

```
第 ① 步 看图   —— 先看字符画，搞懂"到底是什么东西在动"
第 ② 步 跑表   —— 照着「手动推演表」，用手指头把数据走一遍
第 ③ 步 读码   —— 逐行读代码，把注释和你手指走过的路径对起来
第 ④ 步 默写   —— 合上笔记凭记忆写出来，再对照检查
```

90% 的人学不会算法，是因为他们**从 ① 直接跳到 ③**：
一上来就背代码，大脑里没有画面，代码就只是一堆符号而已。

## 第 1 章 二分查找

> **这一节解决什么问题？** 在一个**已经排好序**的数组里，用极少的次数回答"某个值在不在、在哪个位置"。

### 1.1 生活类比：猜数字游戏

我心里想一个 1~100 的数，你来猜，我只回答"大了 / 小了 / 猜对了"。

**笨办法**：从 1 开始一个一个猜，最坏要猜 100 次。

**聪明办法**：

```
猜 50 → "小了"  → 排除 1~50，只剩 51~100   （一出手砍掉一半）
猜 75 → "大了"  → 排除 75~100，只剩 51~74   （又砍一半）
猜 62 → "小了"  → 只剩 63~74
猜 68 → "大了"  → 只剩 63~67
猜 65 → "小了"  → 只剩 66~67
猜 66 → "大了"  → 只剩 67
猜 67 → ✅ 猜到了！一共 7 次
```

这就是二分的全部思想：**每次猜当前范围的"正中间"**。你不需要聪明，只需要遵守规则。

### 1.2 唯一前提（一半的人栽在这里）

> **数据必须有序。**

如果数据乱序，`arr[mid] < target` 判断就毫无信息量 —— 你根本不知道目标在左还是在右。

这也解释了为什么"排序"和"二分"永远成对出现：**排序是二分的入场券。**

### 1.3 第一次看见"指针在动"（核心字符画）

先把三个"状态属性"定义清楚（用 OOP 的话说，它们是同一个对象上的三个字段）：

```
+-------------------------------------------------------------------+
|  left  : 当前"嫌疑区"的左端点（包含这个位置）                        |
|  right : 当前"嫌疑区"的右端点（包含这个位置）                        |
|  mid   : 本轮要检查的位置，正好是 left 和 right 的正中间             |
+-------------------------------------------------------------------+
```

数组 `arr = [2, 5, 8, 12, 16, 23, 38, 56, 72]`，查找 `target = 23`。

#### 初始状态：整个数组都是嫌疑区

```
             left=0                                   right=8
                |                                        |
                v                                        v
索引:    0     1     2     3     4     5     6     7     8
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
arr:  |  2  |  5  |  8  | 12  | 16  | 23  | 38  | 56  | 72  |
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
                               ^
                        mid = (0+8)//2 = 4  →  arr[4] = 16

【第 1 轮】16 vs 23  →  16 < 23，目标在"右边"
                    →  左边这半边（含 16 自己）全部淘汰！
```

#### 第 1 轮之后：`left = mid + 1 = 5`

```
                                                    left=5   right=8
                                                       |        |
                                                       v        v
索引:    0     1     2     3     4     5     6     7     8
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
arr:  |  2  |  5  |  8  | 12  | 16  | 23  | 38  | 56  | 72  |
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
             已淘汰（被砍掉的一半）
                               ^
                        mid = (5+8)//2 = 6  →  arr[6] = 38

【第 2 轮】38 vs 23  →  38 > 23，目标在"左边"
                    →  右边这半边（含 38 自己）全部淘汰！
```

#### 第 2 轮之后：`right = mid - 1 = 5`

```
                                             left=5, right=5
                                                   ||
                                                   vv
索引:    0     1     2     3     4     5     6     7     8
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
arr:  |  2  |  5  |  8  | 12  | 16  | 23  | 38  | 56  | 72  |
      +-----+-----+-----+-----+-----+-----+-----+-----+-----+
      ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^        ^^^^^^^^^^
                    已淘汰                                已淘汰
                               ^
                        mid = (5+5)//2 = 5  →  arr[5] = 23

【第 3 轮】23 vs 23  →  相等！返回下标 5  ✅
```

> **整个二分就三句话：**
> 1. 取中间那个，比一比；
> 2. 比目标小 → `left` 挪到 mid 右边；比目标大 → `right` 挪到 mid 左边；
> 3. 区间缩到不合法（`left > right`）说明**这个值不存在**。

### 1.4 手动推演表（请用手指跟着走一遍）

**场景 A：`target = 23`（能找到）**

| 轮次 | left | right | mid = (left+right)//2 | arr[mid] | 比较 | 状态变化 |
| :---: | :---: | :---: | :---: | :---: | :--- | :--- |
| 初始 | 0 | 8 | — | — | — | 嫌疑区 = `[0, 8]` |
| 第 1 轮 | 0 | 8 | 4 | 16 | `16 < 23` | `left = 4+1 = 5` |
| 第 2 轮 | 5 | 8 | 6 | 38 | `38 > 23` | `right = 6-1 = 5` |
| 第 3 轮 | 5 | 5 | 5 | 23 | `23 == 23` | **返回 5** ✅ |

**场景 B：`target = 40`（找不到）**

| 轮次 | left | right | mid | arr[mid] | 比较 | 状态变化 |
| :---: | :---: | :---: | :---: | :---: | :--- | :--- |
| 初始 | 0 | 8 | — | — | — | 嫌疑区 = `[0, 8]` |
| 第 1 轮 | 0 | 8 | 4 | 16 | `16 < 40` | `left = 5` |
| 第 2 轮 | 5 | 8 | 6 | 38 | `38 < 40` | `left = 7` |
| 第 3 轮 | 7 | 8 | 7 | 56 | `56 > 40` | `right = 6` |
| 结束 | 7 | 6 | — | — | `left > right` | **返回 -1** ❌ |

> **看最后一行**：`left = 7` 却 `right = 6`，区间"前后翻转"了 —— 说明**一个数字都没得看了**。
> 这正是循环终止条件 `while left <= right` 的由来。

### 1.5 逐行拆解代码（写法 A：闭区间 `[left, right]`）

```python
def binary_search(arr, target):
    """
    在升序数组 arr 中查找 target。
    找到 → 返回下标；找不到 → 返回 -1。
    """
    left = 0                      # 左边界：从下标 0 开始看
    right = len(arr) - 1          # 右边界：到"最后一个元素"结束
                                  # 为什么是 len(arr)-1 而不是 len(arr)？
                                  #   因为这是【闭区间】，right 这个位置本身也要被检查。
                                  #   如果写 len(arr)，arr[right] 就越界 → IndexError
                                  #   （len(arr)-1 才是最后一个合法下标，记住这一点）

    while left <= right:          # 只要区间还合法，就继续找
                                  # 为什么是 <= 而不是 < ？
                                  #   闭区间里 left == right 时，还剩【1 个】元素没检查！
                                  #   写成 < 会漏掉最后一个元素 → 本该找到的说找不到

        mid = (left + right) // 2 # 取中点，必须是整除 //，下标只能是整数
                                  # 为什么不用 / ？  4/2 会变成 4.0（float），arr[4.0] 直接 TypeError
                                  # 防溢出小知识：C/Java 里 (left+right) 可能超出 int 上限，
                                  #   安全写法是 left + (right - left) // 2。
                                  #   Python 整数无上限不会溢出，但面试爱考，建议养成习惯

        if arr[mid] == target:    # 命中！直接返回
            return mid

        elif arr[mid] < target:   # 中间值比目标小 → 目标只可能在【右边】
            left = mid + 1        # 为什么是 mid+1 而不是 mid ？
                                  #   arr[mid] 已经确认不等于 target 了，它不可能是答案，
                                  #   排除掉它，区间才真的缩小。
                                  #   写成 left = mid 的话 left 永远不动 → 死循环！

        else:                     # arr[mid] > target → 目标只可能在【左边】
            right = mid - 1       # 同理，mid 这个位置已被"判死刑"，所以是 mid-1

    return -1                     # 循环结束（left > right）还没有返回 → 真的不存在
```

#### 三个"改一个字就会爆炸"的地方（务必看懂）

| 如果你这样写 | 会发生什么 | 为什么 |
| --- | --- | --- |
| `left = mid` | **死循环，程序卡死** | `left` 不前进，区间永不缩小，`while` 永远为真 |
| `while left < right` | **漏掉最后一个元素** | `left == right` 时区间还有 1 个元素，却提前退出了 |
| `mid = (left + right) / 2` | **TypeError 崩溃** | 得到 float，`arr[4.0]` 不合法 |

> **记法**：`left = mid + 1` 和 `right = mid - 1` 里的 `±1`，是对 `mid` 这个"已检查且已淘汰"的位置的**清除标记**。

### 1.6 写法 B：左闭右开 `[left, right)`（Python 官方 `bisect` 用的就是它）

```python
def binary_search_half_open(arr, target):
    """
    在升序数组 arr 中查找 target（左闭右开区间写法）。
    区间语义：left 包含，right 不包含。
    """
    left = 0                      # 左边界：包含
    right = len(arr)              # 右边界：不包含！
                                  # 注意这次是 len(arr) 而不是 len(arr)-1，
                                  # 因为"右开"意味着 right 这个位置本身不在考察范围内

    while left < right:           # 为什么这里变成 < 了？
                                  #   因为区间是 [left, right)，当 left == right 时
                                  #   区间是空的（比如 [3,3) 里没有任何整数），必须停
                                  #   —— 这里的 < 和写法 A 的 <= 是"配套"的，不能混用！

        mid = (left + right) // 2 # mid 仍然取中点
                                  # 因为是右开区间，(left+right)//2 天然落在 [left, right) 内
                                  # 例如 left=0, right=9 → mid=4，合法

        if arr[mid] == target:
            return mid

        elif arr[mid] < target:
            left = mid + 1        # 左边收缩，mid 已排除
        else:
            right = mid           # 【关键区别】右边收缩是 right = mid，不是 mid-1
                                  # 因为 right 本来就不在考察范围内，
                                  # 让 right 指向 mid 就等价于"排除掉 mid"了

    return -1                     # left == right 说明区间空了
```

#### 两种写法的"配套口诀"

```
写法 A  闭区间 [left, right]   →  right 初值 len-1  →  循环用 <=  →  收缩用 mid±1
写法 B  左闭右开 [left, right)  →  right 初值 len    →  循环用 <   →  左收 mid+1，右收缩 mid

【铁律】初值、循环条件、收缩方式，三者必须成套出现，绝不能混搭。
```

> **为什么还要学写法 B？**
> 因为 Python 标准库 `bisect` 和大量"求边界"的题目都用它。而且右开区间在处理空数组时更优雅：`right = len(arr)` 对 `arr = []` 也是 0，不会出现 `-1` 这种诡异下标。

### 1.7 复杂度剖析：为什么是 O(log n)？

**先讲人话版：**

```
n = 1000 时，二分最多查几次？

第 1 次后：剩 500 个
第 2 次后：剩 250 个
第 3 次后：剩 125 个
第 4 次后：剩  62 个
第 5 次后：剩  31 个
第 6 次后：剩  15 个
第 7 次后：剩   7 个
第 8 次后：剩   3 个
第 9 次后：剩   1 个
第 10 次后：剩 0 个（结束）

→ 1000 个数，只要 10 次！
```

**规律**：`2^10 = 1024 ≈ 1000`。

也就是说：**1000 这个数字，只需要 10 次"除以 2"就能变成 1**。

反过来问："**n 要除以多少次 2 才能变成 1？**" —— 这个问题的数学答案就是 `log₂(n)`。

于是：

| 数据量 n | 线性查找（一个个看） | 二分查找 | 差别 |
| :---: | :---: | :---: | :--- |
| 10 | 最多 10 次 | 最多 4 次 | 差别不大 |
| 1,000 | 最多 1,000 次 | 最多 10 次 | 快 100 倍 |
| 1,000,000 | 最多 100 万次 | 最多 20 次 | 快 5 万倍 |
| 1,000,000,000 | 10 亿次 | 最多 30 次 | 快 3300 万倍 |

> **一句话记住**：`O(log n)` = "**每次砍掉一半，砍的次数与 n 的对数成正比**"。
> 更直白地说：**n 每翻一倍，只多查 1 次。**

**正式对比表：**

| 指标 | 二分查找 | 线性查找 |
| --- | :---: | :---: |
| 时间复杂度 | `O(log n)` | `O(n)` |
| 额外空间 | `O(1)`（只用 3 个变量，没开新数组） | `O(1)` |
| 前提 | **必须有序** | 无需有序 |
| 适合场景 | 数据静态、查询极多 | 数据乱序、只查一两次 |

> **注意**：如果"排序"这件事本身要花时间（后面会学，排序是 `O(n log n)`），
> 那么"为了查一次而先排序"是亏的。二分的价值在于：**排一次序，查一百万次**。

### 1.8 OOP 封装版（用你熟悉的方式重写）

把二分封装成一个类 —— 它和你写的任何业务对象没有本质区别：

```python
class SortedArray:
    """
    一个"有序数组"对象。
    把数据（data）和对数据的操作（search）封装在一起。
    left / right / mid 就是它内部流转的状态。
    """

    def __init__(self, data):
        # __init__ 里做一件重要的事：让"有序"这个前提成立
        self.data = sorted(data)      # sorted() 返回【新列表】，不会改调用者传进来的原列表
                                      # 为什么在这里排序？
                                      #   因为"有序"是这个类的【不变式 invariant】——
                                      #   只要对象构造完成，后面所有方法都能放心用二分

    def search(self, target):
        """二分查找：返回下标，找不到返回 -1。"""
        left, right = 0, len(self.data) - 1     # 三个指针就是本次查询的"临时状态"

        while left <= right:                    # 状态判断：区间还有效吗？
            mid = (left + right) // 2           # 状态推导：中点在哪？
            current = self.data[mid]            # 读取当前考察对象

            if current == target:
                return mid                      # 命中 → 提前退出
            elif current < target:
                left = mid + 1                  # 状态迁移：向右收缩
            else:
                right = mid - 1                 # 状态迁移：向左收缩

        return -1                               # 状态终止：区间已空

    def __contains__(self, target):
        # 实现这个魔术方法，就能写 `if 23 in obj:` 了
        # 这正是"把算法封装进 Python 语法"的方式
        return self.search(target) != -1

    def __repr__(self):
        # 定义对象的"打印形态"，调试时一眼看清内部状态
        return f"SortedArray({self.data})"


# ===== 使用 =====
sa = SortedArray([38, 2, 72, 5, 16, 8, 23, 12, 56])   # 故意乱序传入
print(sa)                    # SortedArray([2, 5, 8, 12, 16, 23, 38, 56, 72])
print(sa.search(23))         # 5
print(sa.search(40))         # -1
print(23 in sa)              # True   ← 靠 __contains__ 魔术方法
print(40 in sa)              # False
```

> **OOP 视角的网络小结**：
> - `self.data` = 状态（一个有序容器）
> - `left / right / mid` = 状态（三个游标）
> - `while` 循环 = 状态机
> - `mid = (left + right) // 2` = 状态推导
> - `left = mid + 1` / `right = mid - 1` = 状态转移规则
> - `left > right` = 终止条件
>
> **看出来了吗？"算法"不过是"对象状态在有限步内的流转"。**
> 这就是你要的"在脑海里想象运行过程"的方法 ——
> **不要去想象整个数组，去想象三个变量在跳格子。**

## 第 2 章 递归

> **这一节解决什么问题？**
> 把一个"大到看不完"的问题，变成一个"结构完全相同、只是小一点"的问题。
> 你**不需要知道全部过程**，只需要知道"怎么从这一步走到下一步"。

### 2.1 生活类比：俄罗斯套娃

你手里有一个套娃，打开它，里面还是一个**一模一样的、更小的套娃**。

你要做的事只有两件：

```
①  打开它                    ← 这就是"递归调用"
②  如果是最后一层（打不开了）就停下  ← 这就是"终止条件"
```

**关键洞察**：你不需要知道一共有几层。你只需要会"**开一个娃**"和"**判断是否到底**"这两个动作。

> 这就是递归最反直觉、也最美的地方：**你在写"一次操作"，却自动完成了 n 次。**

### 2.2 递归三要素（缺一个就死循环 / 崩溃）

写任何递归函数前，先在心里把这三格填满：

```
+-------------------------------------------------------------+
|  要素 1  终止条件（base case）                                |
|         什么时候"不用再拆了"，直接给答案。                     |
|         ⚠️ 缺了它 → RecursionError（栈溢出，程序崩溃）          |
+-------------------------------------------------------------+
|  要素 2  递归调用（recursive case）                           |
|         把问题缩小一号，然后"问自己"。                          |
|         ⚠️ 缺了它 → 那就不是递归了，是普通函数                  |
+-------------------------------------------------------------+
|  要素 3  向终止条件靠近（progress）                            |
|         每次调用必须让问题【真的变小】。                        |
|         ⚠️ 缺了它 → 无限递归，栈溢出                            |
+-------------------------------------------------------------+
```

#### OOP 视角：递归 = 对象在自己的方法里调用自己

如果你写过一个树节点类，你其实**早就用过递归**了：

```python
class TreeNode:
    def __init__(self, value):
        self.value = value
        self.children = []        # 一个节点可以拥有若干子节点

    def visit(self):
        print(self.value)                     # 先处理自己
        for child in self.children:           # 再让每个子节点"自己处理自己"
            child.visit()                     # ← 这一行就是递归！
```

**注意这一行**：`child.visit()`。你没有写"遍历整棵树"的代码，你只写了"**一个节点该怎么处理**"。

剩下的，交给了"子节点也是节点"这个事实。

> **递归的本质就是这个**：
> `二叉树` 问题 → 交给 `左子树` 和 `右子树`（它们也是二叉树）
> `阶乘 n!` → 交给 `(n-1)!`（它也是阶乘）
> `斐波那契 fib(n)` → 交给 `fib(n-1)` 和 `fib(n-2)`
>
> **"自己"和"缩小后的自己"，结构完全一样。** 这就是递归成立的全部理由。

### 2.4 逐行拆解代码（阶乘）

```python
def factorial(n):
    """计算 n 的阶乘 n! = n * (n-1) * ... * 2 * 1"""

    # ===== 要素 1：终止条件 =====
    if n <= 1:
        # 为什么是 n <= 1 而不是 n == 0 ？
        #   因为数学上 0! = 1、1! = 1，两者结果一样，写 <= 1 一次性覆盖两个输入。
        #   如果只写 n == 0，那 factorial(1) 会走到下面去算 1 * factorial(0)，
        #   虽然结果也对，但白白多压一层栈。
        #
        # 为什么必须要有这个 if ？
        #   没有它，factorial(-1) → factorial(-2) → ... 永远到不了"底"，
        #   Python 会在约 1000 层后抛 RecursionError 把程序停掉。
        return 1

    # ===== 要素 2 + 3：递归调用，且问题在缩小 =====
    return n * factorial(n - 1)
    #      ↑        ↑
    #      |        └── 参数从 n 变成 n-1，问题真的变小了（要素 3）
    #      └── 本层的待办事项：等"下一层"把答案给我，我再乘上 n
    #
    # 【一个必须想通的问题】为什么 n * factorial(n-1) 里，
    # 前面的 n 不会被覆盖？
    #   因为每一层调用都是【一个独立的栈帧】，里面各有一份自己的 n。
    #   这和 OOP 里"每个实例有自己的 self.属性"是同一件事——
    #   你在类里 new 三个对象，它们的属性互不干扰；
    #   递归里压三层栈，它们的 n 也互不干扰。
```

#### 手动推演表：`factorial(4)`

**阶段一：压栈（一路往下问）**

| 步骤 | 当前层 | 本层在做的事 | 栈内情况（左=栈底） | 本层状态 |
| :---: | :---: | :--- | :--- | :--- |
| 1 | `factorial(4)` | 想算 `4 * factorial(3)`，卡住 | `[4]` | 挂起，等待 |
| 2 | `factorial(3)` | 想算 `3 * factorial(2)`，卡住 | `[4, 3]` | 挂起，等待 |
| 3 | `factorial(2)` | 想算 `2 * factorial(1)`，卡住 | `[4, 3, 2]` | 挂起，等待 |
| 4 | `factorial(1)` | `1 <= 1` 成立 → **直接返回 1** | `[4, 3, 2, 1]` | ★ 触底 |

**阶段二：出栈（一路往上答）**

| 步骤 | 返回的层 | 收到的下层返回值 | 本层计算 | 返回结果 | 栈内剩余 |
| :---: | :---: | :---: | :--- | :---: | :--- |
| 5 | `factorial(1)` | —（自己触底） | 直接 `return 1` | **1** | `[4, 3, 2]` |
| 6 | `factorial(2)` | 1 | `2 * 1 = 2` | **2** | `[4, 3]` |
| 7 | `factorial(3)` | 2 | `3 * 2 = 6` | **6** | `[4]` |
| 8 | `factorial(4)` | 6 | `4 * 6 = 24` | **24** ✅ | `[]` 清空 |

> **用手指模拟一遍**：拿 4 张纸，每张写一个"我欠一个乘法，等人还我"。
> 一路往下码，到最底下一张答出 1，然后**从最上面一张开始往回还债**。
> 这就是"回溯（backtracking）"这个词的由来。

### 2.5 递归树：斐波那契（这里藏着递归最大的坑）

```python
def fib(n):
    """斐波那契数列：0, 1, 1, 2, 3, 5, 8, 13, ..."""
    if n <= 1:            # 要素 1：终止条件
        return n          # fib(0)=0, fib(1)=1
    return fib(n - 1) + fib(n - 2)   # 要素 2+3：两个子问题，都在变小
```

画成树看看 `fib(5)` 发生了什么：

```
                          fib(5)
                        /        \
                   fib(4)          fib(3)
                  /     \         /     \
             fib(3)     fib(2)  fib(2)  fib(1)
             /    \     /   \   /   \
        fib(2) fib(1) fib(1) fib(0) fib(1) fib(0)
         /  \
     fib(1) fib(0)

  【标签】每个节点 = 一次函数调用，等于一个栈帧、一份重复的计算。
```

**数一数：`fib(5)` 居然调用了 15 次！而里面真正"不同"的输入只有 6 种（0~5）。**

重复情况有多夸张：

| 被反复计算的输入 | fib(5) 中出现了几次 |
| :---: | :---: |
| `fib(3)` | 2 次 |
| `fib(2)` | 3 次 |
| `fib(1)` | 5 次 |
| `fib(0)` | 3 次 |

**递归树的分层视角：**

```
第 0 层（根）：                fib(5)              1 个节点
第 1 层：            fib(4)         fib(3)         2 个节点
第 2 层：        fib(3) fib(2) fib(2) fib(1)      4 个节点
第 3 层：    fib(2) fib(1) fib(1) fib(0) ...      8 个节点
第 4 层：  fib(1) fib(0) ...                     16 个节点
                                 ─────────────────────────
                         每层节点数翻倍 → 大约 2^n 个节点
```

> **结论**：朴素的斐波那契递归，时间复杂度是 **指数级 `O(2^n)`**。
> `fib(40)` 就要算十亿次量级，你的电脑要跑几十秒；`fib(100)` 等到天荒地老。

### 2.7 第一次优化：记忆化（把算过的答案记在小本本上）

**思路**：既然 `fib(3)` 会被问 2 次、`fib(2)` 会被问 3 次……那我**第一次算完就记下来**，下次直接查表。

用 OOP 的话说：**给这个"计算器对象"加一个缓存字段（cache）。**

```
【优化前的递归树】                【加缓存后的递归树】

        fib(5)                          fib(5)
       /      \                        /      \
   fib(4)    fib(3)                fib(4)    fib(3) ← 已缓存，直接取！✂️
   /   \     /    \                /   \
fib(3) fib(2) fib(2) fib(1)     fib(3) fib(2)
  ...     ...     ...             /   \
                                fib(2) fib(1) ← 已缓存 ✂️
                                 /   \
                             fib(1) fib(0)
                             ✂️ 已缓存   ✂️ 已缓存

每层节点翻倍 → 约 2^n 次        每个输入只算 1 次 → 约 n 次
```

**代码实现（两种写法）：**

```python
# ---------- 写法 1：用字典当缓存（推荐理解，清晰） ----------
def fib_memo(n, memo=None):
    """
    带记忆化的斐波那契。
    memo 是一个字典：{输入: 算好的答案}
    """
    if memo is None:
        # 为什么用 `memo = None` 再赋值，而不是直接写 `memo = {}`？
        #   ★ 这是一个经典的 Python 陷阱：
        #   如果把 `memo={}` 写在函数签名里（def f(n, memo={})），
        #   这个空字典只会在【函数定义时创建一次】，
        #   之后所有调用都会共享同一个字典！
        #   这是"可变默认参数"陷阱，它会让你的函数在上次调用的脏数据上继续跑。
        #   正确做法就是用 None 占位，在函数体内新建。
        memo = {}

    if n in memo:
        return memo[n]          # ★ 缓存命中：直接返回，不再往下递归（这一步叫"剪枝"）

    if n <= 1:                  # 终止条件
        return n

    # 先算出来，再存进缓存，最后返回
    result = fib_memo(n - 1, memo) + fib_memo(n - 2, memo)
    memo[n] = result            # ★ 记账：把答案写进小本本
    return result


# ---------- 写法 2：用 @lru_cache 装饰器（生产环境写法） ----------
from functools import lru_cache

@lru_cache(maxsize=None)        # maxsize=None 表示"缓存不限量"
def fib_fast(n):
    # 加了装饰器之后，Python 会自动帮你做"查表 / 记账"，
    # 你只需要写最朴素的递归逻辑即可。
    # lru = Least Recently Used（最近最少使用），缓存满了会淘汰最久没用的。
    if n <= 1:
        return n
    return fib_fast(n - 1) + fib_fast(n - 2)
```

**效果对比表：**

| n | 朴素递归 `fib(n)` | 记忆化 `fib_memo(n)` |
| :---: | :---: | :---: |
| 10 | 177 次调用 | 19 次调用 |
| 20 | 21,891 次 | 39 次 |
| 30 | 约 270 万次 | 59 次 |
| 40 | 约 3.3 亿次 | 79 次 |
| 100 | ☠️ 宇宙毁灭也算不完 | 199 次（瞬间） |

**复杂度剖析（为什么从 O(2ⁿ) 变成 O(n)？）**

```
朴素递归：每一次调用都分裂成 2 个调用 → 树是"胖"的 → 节点数 ≈ 2^n
记忆化：  n 一共只有 n+1 种取值（0,1,...,n），
          每种取值最多被"真正计算"一次，其余全是 O(1) 的查表
          → 总工作量 ≈ n 次计算 + n 次查表 → O(n)
```

> **一句话记住**：**记忆化 = 用一点内存（O(n) 的字典），换掉海量的重复计算（2ⁿ → n）。**
> 这就是**动态规划（DP）的起点**。第 3 章我们会把这个思想系统化。

### 2.8 递归 vs 迭代：同一件事的两件衣服

把 `factorial` 用循环再写一遍，你会看到**两者是同一件事的两种描述**：

```python
def factorial_loop(n):
    """迭代版阶乘：用循环代替递归"""
    result = 1                  # 累积器：相当于"从栈底一路带上来的乘积"
    for i in range(2, n + 1):   # 为什么从 2 开始？因为乘 1 没有任何影响，白白多跑一轮
        result *= result ...    # ← 这里故意留个思考：正确写法应该是 result *= i
        # 手动推演 n=4：
        #   i=2: result = 1*2 = 2
        #   i=3: result = 2*3 = 6
        #   i=4: result = 6*4 = 24
    return result
```

> ⚠️ 上面那行 `result *= result` 是**故意写错的**（它算的是不断平方）。
> 请你自己改成 `result *= i`，然后对照手动推演表确认：`2 → 6 → 24`。

**两种写法对照表：**

| 维度 | 递归版 | 迭代版 |
| :--- | :--- | :--- |
| 代码形态 | `n * factorial(n-1)`，短、贴近数学定义 | `for` 循环 + 累积变量 |
| 内存 | **O(n)**：每层压一个栈帧 | **O(1)**：只有 1 个 `result` 变量 |
| 速度 | 慢（函数调用本身有开销） | 快 |
| 可读性 | 定义式问题（树、图）易读 | 线性问题易读 |
| 风险 | 递归超 1000 层就 `RecursionError` | 无栈溢出风险 |
| 能不能改写成对方 | 所有递归都能改写成迭代（自己用栈模拟） | 所有迭代都能改写成递归（但可能没必要） |

**关于"为什么 Python 递归容易爆栈"：**

```
Python 的默认递归上限 ≈ 1000 层
（可用 sys.setrecursionlimit() 调整，但调太大有真实的内存崩溃风险）

而 C / Java / Rust 等语言有"尾递归优化"：
  如果 return 语句里最后一步就是调用自己（没做别的运算），
  编译器就把递归变成循环，栈帧复用 → 不会爆栈。

Python【不做】尾递归优化（Guido 明确表示过不打算加）。
  → 所以在 Python 里，深递归请改写成循环。
```

| 场景 | 建议 |
| :--- | :--- |
| 树 / 图的遍历、分治、回溯（8 皇后、路径搜索） | ✅ 用递归，代码清晰到不可思议 |
| 线性累加、计数、简单数列 | ✅ 用循环，省内存 |
| 数据规模可能上万层深（如链表长度 10 万） | ⚠️ 必须改写成循环，否则爆栈 |

### 2.9 递归版二分查找（分治思想第一次现身）

回到第 1 章的二分 —— 它其实**天然就是分治**：每次砍掉一半，剩下的那一半**还是同样的问题**。

```python
def binary_search_recursive(arr, target, left=None, right=None):
    """
    递归版二分查找：把"在 [left,right] 里找"这个大问题，
    拆成"在更小的 [left,right] 里找"。
    """
    # 第一次调用时，把区间初始化为"整个数组"
    if left is None:
        left = 0
        # 注意这里 right 不能写 0（那会是个 bug），要写 len(arr)-1
    if right is None:
        right = len(arr) - 1

    # ===== 要素 1：终止条件（"区间空了"就是递归的底）=====
    if left > right:
        return -1                 # 没有元素可找了 → 不存在

    mid = (left + right) // 2     # 中间位置

    # ===== 要素 1'：另一个终止条件（命中了）=====
    if arr[mid] == target:
        return mid

    # ===== 要素 2 + 3：递归，且区间在缩小 =====
    if arr[mid] < target:
        # 去右半边找：区间从 [left, right] 变成 [mid+1, right]
        # 注意这里必须 return！否则函数会往下继续执行，
        # 最后隐式返回 None —— 这是递归里极常见的 bug。
        return binary_search_recursive(arr, target, mid + 1, right)
    else:
        # 去左半边找：区间变成 [left, mid-1]
        return binary_search_recursive(arr, target, left, mid - 1)
```

**递归深度分析（对比第 1 章的循环版）：**

```
arr 有 9 个元素，查 target = 23：

binary_search_recursive(..., 0, 8)    ← 第 1 层，区间 [0,8]，9 个元素
        ↓ mid=4, arr[4]=16 < 23
binary_search_recursive(..., 5, 8)    ← 第 2 层，区间 [5,8]，4 个元素
        ↓ mid=6, arr[6]=38 > 23
binary_search_recursive(..., 5, 5)    ← 第 3 层，区间 [5,5]，1 个元素
        ↓ mid=5, arr[5]=23 命中！
      返回 5  ✅

递归层数 = 3，而 log₂(9) ≈ 3.17 → 吻合。
```

| 维度 | 循环版二分 | 递归版二分 |
| :--- | :---: | :---: |
| 时间复杂度 | O(log n) | O(log n) |
| 空间复杂度 | **O(1)** | **O(log n)**（栈帧要占地方） |
| 代码直观度 | 需要理解指针 | 更接近"分治"的直觉 |

> **注意**：递归版二分虽然优雅，但**空间更贵**。
> "分治"的递归深度是 `log n`，不是 `n`，所以深度学习（如快排、归并）里用递归完全没问题 ——
> **只有"线性深度"的递归才危险。**

## 第 3 章 二分 × 递归 = 分治的真身

> **这一节解决什么问题？**
> 把"二分"和"递归"合并成一个通用套路（分治），让你看到一个陌生问题时能立刻反应出：
> **"我能不能把它切成两半，分别解决，再拼起来？"**

### 3.1 分治三步曲（Divide and Conquer）

```
+----------------------------------------------------------------+
|  ① 分解 Divide   ：把大问题切成若干个"同形状"的小问题            |
|                    （通常是切成 2 份，所以叫"二分"）              |
|  ② 解决 Conquer  ：递归地去解决每个小问题                        |
|                    （小到"一眼能看出答案"时，直接返回 —— 终止条件）|
|  ③ 合并 Combine  ：把小问题的答案拼成大问题的答案                |
+----------------------------------------------------------------+
```

**用字符画理解：**

```
                    大问题（n 个元素）
                          │
                     ① 分解：切一刀
                          │
          ┌───────────────┴───────────────┐
          │                               │
     左半边（n/2）                    右半边（n/2）
          │                               │
     ② 递归解决                       ② 递归解决
          │                               │
          ▼                               ▼
       左答案                          右答案
          │                               │
          └───────────────┬───────────────┘
                          │
                     ③ 合并：拼起来
                          │
                     最终答案
```

> **请注意**：二分的"合并"步骤是**空的**（找到了就是找到了，不需要拼）。
> 而归并排序 / 快速排序的"合并"步骤才是重头戏 —— 第 02 章会讲。

### 3.2 案例：快速幂 `x^n` —— 分治把 O(n) 变成 O(log n)

**笨办法**：`x^n` 就是 x 乘 n 次 → 要做 `n-1` 次乘法 → `O(n)`。

**分治视角**：想算 `x^10`，我不用乘 9 次，我可以这样想：

```
   x^10
     │
     ├─ 它有"一半"吗？→ x^10 = (x^5) * (x^5)     ← 算一次 x^5，平方即可！
     │
   x^5 是奇数幂 → x^5 = x * x^4 = x * (x^2)^2
     │
   x^2 = (x^1)^2
     │
   x^1 → 终止条件，就是 x 本身
```

**指数缩小的字符画（n = 10）：**

```
朴素算法：乘 9 次
  x·x·x·x·x·x·x·x·x·x
  └─1─┘└─2─┘└─3─┘└─4─┘└─5─┘└─6─┘└─7─┘└─8─┘└─9─┘     9 步

分治算法：指数每次【减半】，4 步到底
  n = 10  →  n = 5  →  n = 4  →  n = 2  →  n = 1
      │         │         │         │         │
     /2        /2        /2        /2        到底
  （10 是偶数，拆两半） （5 是奇数，拎出一个 x）
```

**逐行代码：**

```python
def fast_pow(x, n):
    """
    计算 x 的 n 次方（n 为非负整数），时间 O(log n)。
    这是"分治"最干净的一个例子。
    """
    # ===== 要素 1：终止条件 =====
    if n == 0:
        return 1              # 任何数的 0 次方都是 1（数学约定）
                              # 为什么是 1 而不是 0？因为 x^0 = x^(a-a) = x^a / x^a = 1

    if n == 1:
        return x              # 最底层：x^1 就是 x，不用再拆

    # ===== 要素 2 + 3：先解决"一半"，再合并 =====
    half = fast_pow(x, n // 2)    # ① 分解 + ② 递归解决：把指数砍一半
                                  #    注意 n // 2 是整除，n=5 时得到 2（丢掉 0.5）

    if n % 2 == 0:
        # n 是偶数：x^n = (x^(n/2))^2
        # 为什么只递归【一次】？因为 x^(n/2) 算一次就够了，
        # 两个半份完全相同，平方比"再调用一次"省一半工作。
        return half * half        # ③ 合并：平方
    else:
        # n 是奇数：x^n = x * (x^(⌊n/2⌋))^2
        # 例：x^5 = x * (x^2)^2  → 拆成一个 x 乘上偶数次幂的情况
        return x * half * half    # ③ 合并：多乘一个 x 补上那"落单"的一次
```

**手动推演表：`fast_pow(2, 10)`，求 2^10**

| 步骤 | 当前调用 | n 的奇偶 | 先做什么 | 得到的 half | 本层返回 | 说明 |
| :---: | :--- | :---: | :--- | :---: | :---: | :--- |
| 1 | `fast_pow(2, 10)` | 偶数 | 先算 `fast_pow(2, 5)` | ？ | ？ | 挂起，等下层的答案 |
| 2 | `fast_pow(2, 5)` | 奇数 | 先算 `fast_pow(2, 2)` | ？ | ？ | 挂起 |
| 3 | `fast_pow(2, 2)` | 偶数 | 先算 `fast_pow(2, 1)` | ？ | ？ | 挂起 |
| 4 | `fast_pow(2, 1)` | — | 命中 `n == 1` | — | **2** | ★ 触底 |
| 5 | `fast_pow(2, 2)` | 偶数 | `half=2` | 2 | `2*2 =` **4** | 回溯 |
| 6 | `fast_pow(2, 5)` | 奇数 | `half=4` | 4 | `2*4*4 =` **32** | 回溯 |
| 7 | `fast_pow(2, 10)` | 偶数 | `half=32` | 32 | `32*32 =` **1024** | ✅ 2^10 = 1024 |

**对比一下乘法次数：**

| 方法 | 2^10 需要的乘法次数 | n 次幂的时间复杂度 |
| :--- | :---: | :---: |
| 朴素连乘 | 9 次 | `O(n)` |
| 快速幂（分治） | 4 步递归，每步约 2 次乘法 ≈ 6 次 | **`O(log n)`** |

> **这就是分治的威力**：它不是在"优化"，
> 而是**换了一个看待问题的角度** —— 从"我要乘 n 次"变成"我要把 n 砍成 1"。
> 后者是 `log n` 步，前者是 `n` 步。

### 3.3 进阶变体：查找"第一个 ≥ target 的位置"（左边界）

**问题**：数组里有很多重复值，我要找**最左边**那个满足条件的。比如排行榜里"第一个不低于 60 分的记录"。

```python
arr = [1, 3, 3, 3, 5, 7]
索引   0  1  2  3  4  5

target = 3  →  答案应该是 1（第一个 3），而不是 3
target = 4  →  答案应该是 4（第一个 ≥ 4 的是 5，在索引 4）
```

**关键思路转变（这一点极其重要）：**

```
【普通二分】  arr[mid] == target 时 → 直接返回 ✓（因为答案唯一）
【左边界二分】arr[mid] == target 时 → 【不返回】，继续往左挤！
              因为左边可能还有相同的值，我要的是最左边那个。
```

**字符画：数组 `[1, 3, 3, 3, 5, 7]`，找 `target = 3` 的左边界**

```
【铁律】用 `>=` 把区间切成两段：左边全是 "< 3"，右边全是 ">= 3"
        答案就是【右段的第一个位置】

索引:     0     1     2     3     4     5
       +-----+-----+-----+-----+-----+-----+
arr:   |  1  |  3  |  3  |  3  |  5  |  7  |
       +-----+-----+-----+-----+-----+-----+
          <3   └──────── >= 3 ────────────┘
                       ↑
                 答案就在这个交界处

━━━━━━━━━━ 第 1 轮 ━━━━━━━━━━
left=0, right=6, mid=3, arr[3]=3

        left=0                 mid=3         right=6
          |                      |              |
          v                      v              v
       +-----+-----+-----+-----+-----+-----+
       |  1  |  3  |  3  |  3  |  5  |  7  |   [6] 是"哨兵"，不参与
       +-----+-----+-----+-----+-----+-----+
                              ^
                    arr[3] = 3 >= 3 → 说明"答案可能在 mid 或者更左边"
                    → 把 mid 保留为候选：right = mid = 3
                    （注意：不是 mid-1！因为 mid 自己就有可能是答案）

━━━━━━━━━━ 第 2 轮 ━━━━━━━━━━
left=0, right=3, mid=1, arr[1]=3

        left=0    mid=1    right=3
          |         |         |
          v         v         v
       +-----+-----+-----+-----+-----+-----+
       |  1  |  3  |  3  |  3  |  5  |  7  |
       +-----+-----+-----+-----+-----+-----+
                    ^
             arr[1] = 3 >= 3 → 还是太大，继续往左：right = mid = 1

━━━━━━━━━━ 第 3 轮 ━━━━━━━━━━
left=0, right=1, mid=0, arr[0]=1

       left=0, mid=0, right=1
          ||
          vv
       +-----+-----+-----+-----+-----+-----+
       |  1  |  3  |  3  |  3  |  5  |  7  |
       +-----+-----+-----+-----+-----+-----+
          ^
     arr[0] = 1 < 3 → 太小了，答案在右边 → left = mid + 1 = 1

━━━━━━━━━━ 收敛 ━━━━━━━━━━
left == right == 1  → 区间空了，循环结束
                      left 指向的位置就是答案：索引 1 ✅
```

**逐行代码：**

```python
def lower_bound(arr, target):
    """
    返回第一个【大于等于】target 的位置。
    如果所有元素都小于 target，返回 len(arr)。
    要求 arr 已升序排序。
    """
    left = 0                      # 左边界：包含
    right = len(arr)              # 右边界：不包含（用左闭右开，收敛更干净）

    while left < right:           # 左闭右开的标准循环条件
        mid = (left + right) // 2

        if arr[mid] < target:
            # mid 的值【太小】，它绝不可能是答案
            # → 答案一定在 mid 右边
            left = mid + 1        # 注意这里是 mid+1：彻底排除 mid
        else:
            # arr[mid] >= target，mid 有可能是答案（甚至可能就是"第一个"）
            # → 所以【不能排除它】，把 right 收缩到 mid
            right = mid           # 注意右闭右开用的是 mid，不是 mid-1

    # 循环结束时 left == right，这个位置就是答案
    return left
```

**手动推演表：`arr = [1, 3, 3, 3, 5, 7]`**

**场景 A：`target = 3`（找第一个 3）**

| 轮次 | left | right | mid | arr[mid] | 判断 | 动作 | 区间含义 |
| :---: | :---: | :---: | :---: | :---: | :--- | :--- | :--- |
| 初始 | 0 | 6 | — | — | — | — | 全数组 |
| 第 1 轮 | 0 | 6 | 3 | 3 | `3 >= 3` | `right = 3` | 答案 ≤ 索引 3 |
| 第 2 轮 | 0 | 3 | 1 | 3 | `3 >= 3` | `right = 1` | 答案 ≤ 索引 1 |
| 第 3 轮 | 0 | 1 | 0 | 1 | `1 < 3` | `left = 1` | 答案 ≥ 索引 1 |
| 结束 | **1** | **1** | — | — | `left == right` | **返回 1** ✅ | — |

**场景 B：`target = 4`（数组里没有 4）**

| 轮次 | left | right | mid | arr[mid] | 判断 | 动作 |
| :---: | :---: | :---: | :---: | :---: | :--- | :--- |
| 初始 | 0 | 6 | — | — | — | — |
| 第 1 轮 | 0 | 6 | 3 | 3 | `3 < 4` | `left = 4` |
| 第 2 轮 | 4 | 6 | 5 | 7 | `7 >= 4` | `right = 5` |
| 第 3 轮 | 4 | 5 | 4 | 5 | `5 >= 4` | `right = 4` |
| 结束 | **4** | **4** | — | — | `left == right` | **返回 4** ✅ |

> 返回值 4 的含义是："**第一个 ≥ 4 的元素在索引 4（值是 5）**"。
> 如果返回 `len(arr)`，说明"整个数组都比 target 小"。

**关于 `bisect` 模块（生产环境直接用）：**

```python
import bisect

arr = [1, 3, 3, 3, 5, 7]

print(bisect.bisect_left(arr, 3))    # 1  ← 第一个 >= 3 的位置（就是我们的 lower_bound）
print(bisect.bisect_right(arr, 3))   # 4  ← 第一个 >  3 的位置
print(bisect.bisect_left(arr, 4))    # 4  ← 数组里没有 4，返回"插入位置"

# 插入操作（保持有序）—— O(n)，因为列表插入本身要挪动元素
bisect.insort(arr, 4)
print(arr)                           # [1, 3, 3, 3, 4, 5, 7]

# 小技巧：用 bisect_right - bisect_left 统计重复元素个数
print(bisect.bisect_right(arr, 3) - bisect.bisect_left(arr, 3))   # 3 个 3
```

> **记忆口诀**：
> `bisect_left` 找的是"**>=** 的分界线"，`bisect_right` 找的是"**>** 的分界线"。
> 两者相减 = 这个值出现了几次。

## 第 4 章 常见坑清单

> **这一节解决什么问题？** 把"你已经踩过 / 将要踩"的坑提前列出来，让你写代码时**带着检查清单**，而不是写完报错再猜。

### 4.1 二分的四个经典坑

| # | 坑 | 症状 | 根本原因 | 修法 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | `left = mid`（没 +1） | 程序卡死、风扇狂转 | `left` 不前进，区间永不缩小，`while` 永远为真 | 改成 `left = mid + 1` |
| 2 | 混搭两种写法 | 找不到明明存在的元素 | 闭区间的初值配了开区间的循环条件，配套关系被破坏 | 初值 / 循环条件 / 收缩方式，**三件套必须同源** |
| 3 | `mid = (left + right) / 2` | `TypeError: list indices must be integers` | `/` 得到 float，不能当下标 | 用整除 `//` |
| 4 | `arr` 没排序就用二分 | 结果时对时错，非常"玄学" | 前提被破坏，判断无意义 | 先 `sorted()`（或确认数据本来有序） |

**配套关系速查（贴在显示器上）：**

```
┌──────────────────────┬────────────────────────────┐
│ 写法 A：闭区间        │ 写法 B：左闭右开            │
├──────────────────────┼────────────────────────────┤
│ right = len(arr) - 1 │ right = len(arr)           │
│ while left <= right  │ while left < right         │
│ left = mid + 1       │ left = mid + 1             │
│ right = mid - 1      │ right = mid                │
│ 返回时需要判断存在性   │ 返回 left 即为"插入点"      │
└──────────────────────┴────────────────────────────┘
         ↑ 每一列内部是"成套"的，跨列混搭 = bug
```

> **一个救命小技巧**：写二分时，**先在纸上用长度为 1 和 2 的数组手推一遍**。
> `[5]` 查 5、`[5,6]` 查 6 —— 这两个 case 能筛掉 90% 的边界错误。

### 4.2 递归的四个经典坑

| # | 坑 | 症状 | 根本原因 | 修法 |
| :---: | :--- | :--- | :--- | :--- |
| 1 | 忘了写终止条件 | `RecursionError: maximum recursion depth exceeded` | 一路往下钻，没有"底" | 补 `if` 终止分支 |
| 2 | 递归调用没让问题变小 | 同上（栈溢出） | 参数没变，等于原地转圈 | 检查参数是否真的在靠近终止条件 |
| 3 | 递归分支忘了 `return` | 结果变成 `None` | 函数执行到尾部隐式返回 `None`，把正确的返回值覆盖了 | 递归调用前加 `return` |
| 4 | 可变默认参数 `def f(memo={})` | 上一次调用的脏数据污染这次 | 默认参数只在**定义时**创建一次，被共享 | 用 `def f(memo=None)` 再在内部 `if memo is None: memo = {}` |

**坑 3 的具体样子（这个 bug 极其常见）：**

```python
# ❌ 错误写法
def bad(arr, target, left, right):
    if left > right:
        return -1
    mid = (left + right) // 2
    if arr[mid] == target:
        return mid
    if arr[mid] < target:
        bad(arr, target, mid + 1, right)    # ← 少了 return！
        # 这行调用会算出正确结果，但结果被直接丢弃，
        # 函数继续往下走，最后隐式 return None

# ✅ 正确写法
def good(arr, target, left, right):
    if left > right:
        return -1
    mid = (left + right) // 2
    if arr[mid] == target:
        return mid
    if arr[mid] < target:
        return good(arr, target, mid + 1, right)   # ← 加上 return
    return good(arr, target, left, mid - 1)
```

### 4.3 写代码前的"30 秒自查清单"

```
【二分自查】
□ 数组有序吗？
□ right 的初值是 len-1（闭）还是 len（开）？和我的循环条件配套吗？
□ 循环条件是 <= 还是 <？和 right 的初值配套吗？
□ 收缩时是 mid±1 还是 mid？和区间语义配套吗？
□ 用 [5] 和 [5,6] 这两个边界数组在心里跑过了吗？

【递归自查】
□ 终止条件是什么？它在什么输入下会被触发？
□ 每次递归调用，参数有没有真的变小？
□ 递归调用前面有 return 吗？
□ 递归深度大概是多少？（如果是 O(n) 且 n 可能上万，改成循环）
□ 有没有重复计算？（有的话考虑加缓存）
```

## 速查卡

### 一、二分查找（闭区间版，直接背）

```python
left, right = 0, len(arr) - 1

while left <= right:              # 1. 区间还有元素
    mid = (left + right) // 2     # 2. 取中点
    if arr[mid] == target:
        return mid                # 3. 命中
    elif arr[mid] < target:
        left = mid + 1            # 4. 去右边（排除 mid）
    else:
        right = mid - 1           # 5. 去左边（排除 mid）

return -1                         # 6. 不存在
```

### 二、递归模板（填空法）

```python
def solve(问题, 规模):
    if 规模 是最小规模:            # ← 要素 1：终止条件
        return 直接能得出的答案

    子答案1 = solve(问题, 更小的规模)   # ← 要素 2 + 3：递归 + 缩小
    子答案2 = solve(问题, 更小的规模)

    return 把子答案合并起来         # ← 合并（分治）
```

### 三、复杂度速查

| 复杂度 | 人话解释 | 典型算法 |
| :---: | :--- | :--- |
| `O(1)` | 一眼就知道答案，跟数据量无关 | 数组按下标取值 |
| `O(log n)` | **每次砍一半**，n 翻倍只多 1 步 | 二分查找、快速幂 |
| `O(n)` | 每个元素看一眼 | 线性查找、求和 |
| `O(n log n)` | 每个元素都经历 log n 次"分合" | 归并排序、快速排序（平均） |
| `O(n²)` | 两层循环，两两配对 | 冒泡排序、选择排序 |
| `O(2ⁿ)` | **每次分裂成 2 个**，指数爆炸 | 朴素斐波那契递归 |
| `O(n!)` | 全排列，比指数还恐怖 | 暴力旅行商问题 |

> **判断口诀**：
> "**每次砍一半**" → `log n`；"**每次分裂成几个**" → 指数；"**几个循环嵌套**" → 多项式次数。

### 四、OOP 映射表（本章核心方法论，随时回看）

| 算法概念 | OOP 对应 |
| :--- | :--- |
| 数组 / 树 / 图 | 对象或对象集合 |
| 指针 / 数组下标 | 对象的**状态属性** |
| 循环的一轮 | 一次**状态迁移** |
| 递归调用 | 对象在自己的方法里**创建并调用同类对象** |

| 记忆化缓存 | 对象里的一个 `dict` **缓存字段** |
| 分治 | 模板方法模式：父类定义"分解-解决-合并"骨架 |

### 自测题 1（基础巩固 · 二分）

给定有序数组 `arr = [1, 4, 6, 9, 13, 18, 22, 27, 35]`：

1. 手写一个**闭区间版**的二分查找函数，逐行写出中文注释。

4. 回答：如果数组长度是 **1024**，二分最多比较几次？说出你的推导过程（不要只写答案）。

### 自测题 2（进阶迁移 · 递归 + 缓存）

**爬楼梯问题**：你面前有 `n` 级台阶，每次你只能走 **1 级** 或 **2 级**。请问走到第 `n` 级一共有多少种**不同的走法**？

（例：`n = 3` 时答案是 3 种 —— `1+1+1`、`1+2`、`2+1`）

要求：

1. 用**递归**实现 `climb(n)`，并写清你的**递归三要素**（终止条件是什么？为什么？）。
2. 在纸上**画出 `climb(5)` 的递归树**，并数一数你一共调用了多少次函数。
3. 在递归树里**圈出所有被重复计算的子问题**，并说明如果你加一个缓存，调用次数会减少到多少次。
4. 挑战：这道题的递推关系和本章的斐波那契有什么关系？为什么？
