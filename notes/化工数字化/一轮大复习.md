# 化工实验数据项目

## 组成
- **MySQL 数据库**：在这项目做为“大冰箱”，作用是存所有实验数据（永不丢失）
- **Models.py**: 作为“图纸”，定义一条实验记录长什么样
- **Storage.py**：作为“搬运工”，负责从冰柜拿东西、往里面放东西
- **App.py**:作为“服务员”，接收外部请求，端菜上桌（API）
- **Predict_optimal 逻辑**: 作为“数学家”，算出最优温度
- **Matplotlib**：作为“画师”，画出漂亮的趋势图
- **Test_*.py + pytest**:作为质检员，每个环节都要测试一遍
- **Git/Github**: 作为“仓库管理员”，保留所有版本历史
- **Github Actions**:作为“自动工人”，每次推代码，云端自动跑测试
- **Docker**:作为“集装箱”，打包整个酒楼，搬到任何电脑上都能开


## 分层逻辑（分成架构）

### 核心架构思想:

```text
┌─────────────────────────────┐
│   用户/网页/Apifox 发请求     │  ← 交互层
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│   app.py（FastAPI 接口）      │  ← 接口层（接收请求）
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│   storage.py（存/取数据）     │  ← 存储层（负责读写）
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│   models.py（Experiment类）   │  ← 模型层（定义数据）
└──────────────┬──────────────┘
               ↓
┌─────────────────────────────┐
│        MySQL 数据库          │  ← 持久层（真正存盘）
└─────────────────────────────┘

```
- 好处：代码一层一层搭起，改代码相互不会影响，方便，“高内聚，低耦合”


### 数据结构演变

|阶段  |	数据结构|	例子	|为什么是这个|
|----------|-----------|----------|-------------|
|1. 数据库|	二维表（行+列）|	id 、 name 、 temp 、 yield|	存盘最稳定|
|2. Python内存|	类的对象|	Experiment(temp=150, yield=88)	|操作方便，有属性|
|3. 传给Pandas|	字典列表|	[{"温度":150, "收率":88}]	|Pandas爱吃的格式|
|4. Pandas处理|	DataFrame|	一张二维表|	能做筛选、排序、统计|
|5. 传给API	|JSON字符串|	{"temp":150, "yield":88}|网络传输标准格式|

## 语言逻辑

### 1.面向对象（OOP）
```python
class Experiment:
    def __init__(self, exp_id, temperature, ...):
        self.exp_id = exp_id
        ...

```
- 不能用字典存：因为字典是散装的、类可以将各种方法打包在一起，可以继承、复用，传参更清晰，更直观

### 2.函数（为什么要把代码装进def里面）

- 核心思想：DRY（Don't Repeat Yourself）。
你写了 100 次查询数据库的代码，如果哪天数据库地址变了，你要改 100 次。
写成函数后，改一次，全部生效。
```python
def load_experiments(db_name="chemical_lab"):
    ...

```
### 3.异常处理（trt/except）

- 优点：因为程序不能动不动就崩溃。 大厂系统里，网络、数据库、用户输入，随时都可能出错。你必须想好“出错了怎么办”。
```python
try:
    conn = pymysql.connect(...)
except pymysql.MySQLError as e:
    print(f"连接失败：{e}")

```

### 5.Matplotlib 画图的“死规矩”
|规矩|为什么|
|------------|---------|

## 设计思想

|问题|为啥这样设计|
|------------------|--------------------|
|为什么用类而不是字典？|数据+行为打包，可扩展，可继承|
|为什么分那么多文件？|改一处不影响全局（低耦合）|
|为什么测试要单独写文件？|	测试和生产代码分离，不污染主程序|
|为什么密码写进 .gitignore？	|防止敏感信息泄露到 GitHub|
|为什么用 fixture？	|每个测试开始前自动清理环境，保证幂等|
|为什么用 BaseApi 封装？|	以后加 100 个接口，不用重复写 requests.post|
|为什么要写 Dockerfile？|换电脑、换系统，一键原样运行|
|为什么要用 GitHub Actions？|	云端自动跑测试，防止忘测|
